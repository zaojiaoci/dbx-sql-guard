# 在真实宿主里验证

回到 [README](../README.zh-CN.md) · [English](verify-on-real-host.md)

1. 安装 DBX（本次验证针对 v0.6.38），并开启「允许未签名的开发包」。
2. 安装 `.dbxp`，打开 **DBX SQL Guard** 工作台，执行一条不带 `WHERE` 的
   `DELETE`：结果必须是 `high` 且 `pending`。
3. 点「批准」。审批人那一栏必须是**空的**，下面有一行提示说明提交人是你、并指向
   规则页的开关。此时填自己的名字必须被**拒绝**，提示 "cannot also approve it"——
   这是 `requireDistinctApprover` 在生效。换成任何一个别的名字就必须能通过；然后点
   「校验链」确认链完整，再对同一条记录审批一次，现在必须被拒绝。弹窗里显示的必须
   是你输入的原样 SQL 并标明"仅本次会话"，而审计列表里显示的是脱敏文本。
4. 再提交一条不带 `WHERE` 的 `DELETE`，点「驳回」，审批人保持预填的自己的名字：
   必须能通过。驳回自己的记录是允许的，批准自己的记录不是。
5. 在 SQL 框里输入 `DELETE FROM`——不带表名——点「写入审计留痕」。必须被拒绝，
   报告面板里要出现 `incompleteStatement` /「语句不完整」这条命中项，并且记录
   总数不能增加。
6. 在插件中心 → 已安装 → **内置 AI 工具** 里确认三个 `sql_guard_*` 工具都在。
   文档说 MCP 工具是随「已打开的插件连接」提供的，而本插件没有声明
   connection provider，所以「没有连接提供点时工具是否仍会出现」未能在真实宿主
   上确认。
7. 在「操作人」里填一个名字，关掉工作台再打开：名字必须还在。这一步走通了
   `host.storage` 权限的完整链路。
8. 在「规则」页的按库审批人里填 `prod = 另一个人` 并保存，重新打开面板必须看到
   同样的一行。此后 `prod` 的记录只有那个人能批；把名字删掉再保存，`prod` 就
   变成谁都批不了——包括全局名单里的人。
9. 随便分析一条语句，点右边 **AI 预审** 卡片里的「生成预审意见」。宿主必须弹窗要你
   确认，然后回复要按它自己的 Markdown 结构显示出来——标题、列表、`代码`、**加粗**、
   围栏代码块都在。如果它提示解析不出模型，卡片会把 `listModels()`
   和 `listProviders()` 的真实返回打印出来——靠这段输出才能分清"没配提供商"和"配了但
   字段名不一样"（见[未能在真实宿主上核实的部分](host-integration.zh-CN.md#未能在真实宿主上核实的部分)）。
10. 点「在 AI 对话中继续」。结果必须是三者之一：打开对话并已自动发出；打开对话并
    提示你自己点发送；或者两次都失败，把宿主原话和发过去的参数留在卡片里。卡片里
    写的是什么，原因就在哪里——这条路径在「生成预审意见」可用的宿主上被反馈为失败过。
11. 在侧边栏右键一张表，选 SQL Guard 那一项。SQL 框此刻必须已经带着一句**被注释掉的**
    `SELECT`，写着的正是这张表连同它真实的模式名——原样点 **Analyze**，报告必须说
    「没有可分析的语句：输入里只有注释和空白」，**不许**出现风险徽章或「自动通过」：给一段
    从来不是语句的文本下一个低风险的结论就是在说谎。把行首那两个连字符删掉，它才变成你能审的
    语句；把框清空，同一张表不该再把模板塞回来。「宿主到底告诉了我们什么」卡片此刻必须
    已经带着递给它的连接和表名，点一次 **Analyze** 之后，方言和计划支持那一行就该填上——
    那是它自己去读了 `getPlanCapabilities` 和 `getTableMetadata`，不用人点。如果改从插件中心
    或底部面板进来，`context` 只有 `{workbenchId, restored, surface}`——没有连接——
    「读取估算计划行数」会是**禁用**状态，卡片的可用性提示行（就在状态行上面）写明为什么，
    那是入口的性质，不是故障。把连接的
    **显示名**粘进去是没用的，宿主会顶回一句 `Connection config not found`。
    如果打回来的是 `Connection is not open`，那是宿主说得对，不是 bug——
    先在 DBX 里把那条连接打开再调一次。那三颗手工摊开宿主原始返回的按钮（bridge 探测、
    `getPlanCapabilities`、`getTableMetadata`）还留在标记里，被 `ui/index.html` 的
    `SHOW_HOST_DIAGNOSTICS` 开关藏着；需要分清"什么都没配"和"配了但字段名不一样"时，
    把它改成 `true` 就叫回来。
12. 还是从那个右键入口进来，在 SQL 框里写 `UPDATE <那张表> SET nope = 1` 再分析。
    报告必须出现 `unknownColumn`，**并且**带上写明用了哪张表、多少个列的那一行。
    改从插件中心重新分析同一段文本：那条命中项必须消失，那一行改说这次没有元数据，
    而其余命中项一条都不能少。如果 `nope` 其实是真实存在的列，两个入口都不许报它。
13. 把输入法切到中文，敲 `UPDATE t SET a = 1；UPDATE t SET b = 2；` 再分析。报告必须写
    **1 条语句**（这正是这条命中项要暴露的东西，不是 bug），并且带一条点名 `；(2)` 的
    「语法位置上出现了全角标点」。同一句发进审计链必须还能成功。然后再敲
    `UPDATE 用户 SET 备注 = '中文，里面有；' WHERE id = 1`——这条一个全角命中项都不许出。
14. 仍然从那张表的右键菜单进来，并且先在 DBX 里把这条连接打开。框里只放**一条** `SELECT`，
    点 **Analyze**，再点「读取估算计划行数」。卡片上此刻应该已经写着方言和「估算计划：支持」，
    原始计划必须原样打出来。随后行数出现在「预估行数」里，下一次报告的命中项会写明这个数字
    来自宿主的估算计划。把框换成 `DELETE FROM <那张表> WHERE <一个真实列> = 1` 再分析：卡片
    此刻必须先显示**探针**——`SELECT * FROM <那张表> WHERE <一个真实列> = 1`——然后点按钮送去
    宿主的必须正是这段文本。下一次的报告要把数字归因于一次**改写**，而不是那条 `DELETE`。
    接着试 `UPDATE t, u SET a = 1 WHERE b = 2`：没有探针，并且要说出拒绝的原因（`multiTable`），
    而且必须弹成 toast，不能只写在卡片里——没人看见的拒绝正是 0.2.1 修掉的那个毛病，新增的
    每一道门都还得守它）。再试 `SELECT 1; SELECT 2`：
    同样在本地被拒——一条语句的
    计划不是整段脚本的估计。最后，读取成功之后改动 SQL：那个数字必须消失，而不是带着旧计划
    跑到新文本上。
15. 还是那个右键入口，审一段**同一个库里另一张表**的语句
    （`DELETE FROM <另一张表> WHERE <一个真实列> = 1`），点「读取估算计划行数」。它必须成功。
    `database` 和 `schema` 说的是**被右键那张表**住在哪儿，把这套作用域钉到另一张表的探针上，
    就是让宿主到一个不含它的命名空间里去找，回报「不存在」——那句报错读起来像用户把表名写错了，
    原因却很可能只是插件把范围收窄了。只有点名了那张被右键的表的探针才允许带上 context 的作用域，
    其余一律交给连接自己的默认；表真的够不着时，宿主那句拒绝就是该看的结果。
