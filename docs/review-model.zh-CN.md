# 判定模型：身份、审批、脱敏

回到 [README](../README.zh-CN.md) · [English](review-model.md)

## 操作人身份

宿主不会把任何身份信息交给插件。这一点是在 DBX 0.6.38 上实测确认的，不是推测：
工作台里的 `window.dbxPlugin.context`，一次进来是 `{}`，另一次是
`{workbenchId, restored, surface}`，而 bridge 的 41 个 key 中没有
user / account / session 之类的字段。就算宿主真的往 `context` 里写了有用的东西——从某张表
的右键菜单进来时，里面会有 `connectionId` 和表名——那些说的也是**数据**，不是
**谁在问**。所以 `operator` 和 `approver` 都是**自报**的——
工作台问一次名字、记住它、然后随请求带上。

- 名字存在宿主 storage 的 `sqlGuard.operator` 键下，这也是 manifest 里声明
  `host.storage` 权限的原因。它跟着这台机器上的 DBX 走，重装插件不会丢，
  也不会混进审计数据库。
- 拿不到宿主 storage 时（旧宿主，或权限被拒），界面会如实说明，此时名字只在
  工作台打开期间有效。
- MCP 调用来自内置 AI，现场没有人可以问，所以继续走 sidecar 的兜底：
  `USER`（或 `USERNAME`）拼上主机名，形如 `user@host`；两者都拿不到时写
  `"unknown"`。带上主机名是为了把"哪个账号"升级成"哪台机器上的哪个账号"——
  多人共用一台机、或同名账号分散在多台机时，光有账号名是分不开的。
  这仍然只是**上下文**，不是认证：账号和主机名都来自本机环境。

哈希链证明的是"记录事后没被改过"，不证明"是谁敲的"。请把这条留痕当作意图与评审
历史的证据，不要当作抗抵赖手段。

## 谁可以审批

两道规则都在 `GuardStore::decide` 里执行，所以所有调用方——工作台、MCP 工具、
将来的远端存储——都过同一道门。两者都返回 JSON-RPC 的 `-32602`，message 是写给
人看的，而不是 `-32000` 内部错误：被拒是调用方能自己处理的事，不该被报成插件故障。

**审批人不得与提交人相同。** 默认开启（`requireDistinctApprover`）。名字比较前会
trim 并转小写，所以 `Alice` 批不了 `alice ` 提交的记录。只有你一个人用这个插件时
才需要在规则页关掉它——否则你永远批不了自己提交的东西。它拦不住两个人互相批准，
因为两个名字都是自报的。

**这条规则只管批准，不管驳回。** 提交人始终可以驳回自己的记录：驳回不授予任何
权限，挡住它只会让记录永远卡在 `pending`，没人能关掉——单人使用时第一个撞到的
就是这个，因为审批弹窗以前会把提交人自己的名字预填进审批人框。现在两者会撞上时
那一栏留空，并说明原因。下面的审批人名单对驳回同样生效：驳回虽然不授权，但它
改写了审计记录，名单外的人不该有这个动作。

**审批人可以限制，全局限制或按库限制。** 全局名单为空表示不限制，谁都能批；一旦
填了名字，就只有名单里的人能批。列在 `scopeApprovers` 里的库**只**认自己那份名单，
不再退回全局名单，所以"只有 DBA leader 能批 `prod`"这条规则在存在全局名单时依然
成立。

"空名单"在两个位置的含义不同，这是有意的：

| 配置 | 含义 |
| --- | --- |
| `approvers` 为空 | 不限制，谁都能批 |
| `scopeApprovers` 里没有 `prod` | 退回 `approvers` |
| `scopeApprovers` 里有 `prod` 但名单为空 | **没有人**能批 `prod` |

最后一行是 fail-closed。审批配置出错时结果只能更严，不能更松——否则把 `prod` 的
名字删掉就等于悄悄把它交给了全局名单。

规则页用"一行一个库"的形式编辑 `scopeApprovers`：`prod = alice, bob`。没有 `=` 的
行会被丢掉而不是去猜用户想配什么，保存后面板会按 sidecar 实际存下的内容重绘，
所以被丢掉的那一行会当场消失，用户能看出来它没被接受。

按库的限制继承了作用域标签本身的局限：没填库名的记录只能对全局名单做校验。

## 审计库里存的是什么

`sql` 列存的是 `risk::redact_literals` 的输出，不是你输入的原文。字符串字面量和
注释内容变成 `?`；标识符、引号标识符和**数字原样保留**：

```sql
-- 提交的
DELETE FROM orders WHERE created_at < '2024-01-01' AND token = 'hunter2' LIMIT 100
-- 存下来的，也是 AI 预审看到的
DELETE FROM orders WHERE created_at < '?' AND token = '?' LIMIT 100
```

为什么数字要留下来：早先的版本把数字也脱敏了，结果拿掉的正好是审批人唯一需要的
信息。`WHERE id = ?` 和一条全表更新看不出区别，替它做预审的模型处境相同。这个取舍
是明说的——数字本身也可能敏感（账号、手机号）——但对一个唯一职责就是预审的工具来说，
"谁都判断不了影响范围"是更糟的失败。把脱敏做成可按规则配置的开关是下一步该做的事，
现在还没做。

脱敏发生在写入之前，所以内容摘要覆盖的是脱敏后的文本。`sql_hash` 则是按**原文**算的，
这就是为什么只有字面量不同的两条语句哈希仍然不同，而它们存下来的文本长得一样。

链只能追加，所以原文事后补不进去。唯一的例外是**本次工作台会话里**刚提交的记录：
它的原文还在浏览器内存里，审批弹窗会显示出来，并标明"不会写入审计库"。关掉工作台
就只剩脱敏文本了——这是"不让审计库变成密码本"的价格。要让旧记录也能看到完整原文，
就得在提交时显式选择保留，那是产品决策，不是缺陷。

### 文件在哪儿，界面上显示哪一份

`guard/ping` 报两次位置：`store` 是绝对路径，`storeDisplay` 把 home 前缀折成 `~`
（`fold_home` 在 home 为空、或路径只是**开头长得像**隔壁目录时拒绝折叠）。审计列表下面
显示折叠版，绝对路径悬停即现，**复制完整路径**那颗按钮写进剪贴板的是绝对版——把带 `~`
的那份粘进 shell 是错的。页眉只留插件名和版本号。

理由：这是摆放位置的问题，不是保密的问题。每条记录本来就写着操作人，而操作人兜底就是
`USER@hostname`，能读留痕的人本来就看得到用户名；这条路径也从不送到模型服务商——MCP 工具
答的是记录，不是文件系统。但审批界面是要被截图外发的东西，而"我在备份哪个文件"是审计页
的问题。

## 什么进不了审计链

链只能追加，写坏的记录事后拿不出来，所以校验必须发生在写入之前。`guard/submit`
和 MCP 的 `sql_guard_record_review` 都会先调 `risk::check_recordable`，遇到下面
两种情况就以 `-32602` 拒绝：

- 整段输入一条语句都没有（只剩空白和注释）；
- 有任何一条语句结尾停在悬空的子句关键字上——`DELETE FROM`、`UPDATE t SET`、
  `SELECT * FROM t WHERE`、`DROP TABLE`。

这样的语句会以 High 风险报一条 `incompleteStatement`。`guard/analyze` 仍然照常
返回完整报告，因为看到"为什么"才是重点；被拦住的只有写入这一步。工作台被拒时会
自动补跑一次分析，让这条命中项出现在报告面板里，而不是只留一个 toast。

这是启发式，不是解析器。关键字表里只放"合法语句绝不可能以它收尾"的词——`end`
被排除，因为 `SET x = CASE … END` 是完整的；带引号的标识符也被排除，因为
`DELETE FROM "on"` 里的 `"on"` 是一张叫 `on` 的表。结尾停在普通标识符上的半成品
（`DELETE FROM t WHERE x =`）仍然会漏过去。这条规则不受任何检测器开关控制：
记录截断的 SQL 没有任何正当理由，加个开关只会多一种误关的可能。
