# 已知限制（完整版）

回到 [README](../README.zh-CN.md) · [English](known-limits.md)

README 里是短清单。这一页留下每条限制背后的理由——这个插件的价值取决于你能相信它对什么说了"不"。

- 只是建议性的（见 README）；拦不住任何一条语句真的被执行。
- `operator` 和 `approver` 都是自报的、未经认证——见
  [操作人身份](review-model.zh-CN.md#操作人身份)。[谁可以审批](review-model.zh-CN.md#谁可以审批) 里的规则强制的是
  **名字上的分离**，不是人的分离。
- 半成品语句的拦截是词法层面的——见[什么进不了审计链](review-model.zh-CN.md#什么进不了审计链)。
- AI 预审意见出自本插件控制不了的模型、不落库、且仅供参考——见 [AI 预审](host-integration.zh-CN.md#ai-预审)。
  它需要 `host.ai` 权限，也需要宿主真的提供 `bridge.ai`；没有的话卡片会如实说明，
  两个按钮保持灰态。
- SQLite 文件是明文，而且可以被整个删掉。链能发现被改和被删的行，发现不了
  文件本身消失（那时 `checked` 为 0 而 `ok` 仍为 true）。
- 单次导出最多 10000 行，因为整份 CSV 是作为一条 JSON-RPC 消息传输的，受协议
  8 MiB 上限约束。响应里会给出 `exported` 和 `truncated`，界面也会如实提示，
  不会让人误以为拿到了全量。
- 决定是一次性的：已批准或已驳回的记录不能再次审批。要纠正错误只能重新提交一条
  记录，而不是改写历史。
- 行数估计有两种来源：宿主的计划（直接给那条语句的计划，或者给引擎为写语句改写出来的
  只读探针的计划），以及调用方自己声明的数字。命中项的消息里会写明是哪一种，来自探针的
  会额外写明这是一次改写。两种都没有时大扫描规则不会触发——这里的沉默是"没有输入"，
  不是"很小"。
- **可用性现在已经是判定的一部分。** 从表的右键菜单进来评的那条语句，可能带着同样的
  文本在插件中心里评不出来的命中项——因为只有前者给得出 `connectionId`。报告里那一行
  写明模式的话，是唯一能把两次运行区分开的东西，所以要比对判定就得用同一个入口进来。
  另外新增的 `host.schema:read`、`host.plans:read` 两个权限会让 DBX 在你安装 **0.2.x 及以后**
  的构建时重新征求同意——从 0.1.1 或更早升上来等同于一次新装，不是原地覆盖。
- **写语句的数字是一次改写换来的。** DBX 的计划门除 Oracle 外对所有方言都拒绝 DML，所以
  插件让宿主计划的是它替这条写语句改写出来的**只读 `SELECT`**
  （[宿主的估算计划](host-integration.zh-CN.md#宿主的估算计划)）。它依赖的等式是「这条写语句碰到的行 = 它的谓词匹配
  的行」——单表 `UPDATE`/`DELETE` 成立，没有 `WHERE` 时就是整张表，也成立；等式不成立的每一种
  形状，引擎拒绝给出探针，并把拒绝的原因说出来。`INSERT` 不在覆盖范围内：计划能读出来源查询
  扫了多少行，读不出这条写入最终落下多少行。没有探针时，影响面仍然只能由人判断，或者由提交者
  自己声明一个数字并被如实标注成"未经检验"。
- 估算计划是**这条连接的优化器给的一个猜测**，不是测量：它按当前的统计信息算，而探针是一条
  `SELECT`——所以它说的是多少行**匹配**，不是这条写语句实际会动多少行：触发器、外键级联、
  `RETURNING` 那些都不在里面。命中项的消息会点明这是一次改写，审批人就不会把它误当成写语句
  自己的计划。它只被用来**提高**一条命中项，从不被用来豁免一条。
- 引擎是词法分类器而不是解析器：不认识的方言语法会被保守评级，但仍可能判错。所以它
  永远证明不了一条语句是**合法**的 SQL，只能证明它**不可能**合法。后者由五条跨方言的
  形状规则负责（finding 代码 `malformedStatement`，Medium，不给开关，而且刻意不作为
  拒绝入库的理由）：`DELETE` 后面跟 `*`、`FROM` 后面跟 `*`、`DELETE` 没有 `FROM`、
  `UPDATE` 没有 `SET`、`INSERT` 没说要插什么值。这挡的就是
  `delete * from user where id = 3`——早先的构建把这条判成 Low，一路放行。要补上剩下的
  那一大块，得靠真正的方言语法（离线的 `sqlparser` crate）。宿主自己的 `explainPlan` 现在
  只接了一个数字（见[宿主的估算计划](host-integration.zh-CN.md#宿主的估算计划)），它既不会替语句做语法检查，也够不到
  写语句。
- **全角标点有专门的命中项**（`fullWidthPunctuation`，和形状规则同一档：Medium、不给开关、
  也不作为拒绝落库的理由）。它要为中文输入法的那一次失误负责：`；`、`，`、`（）`、`－`
  和弯引号都不是 SQL 语法，而语句只按半角 `;` 切分，所以句尾多出来的那个 `；` 会把后面
  整块内容并进这一条语句里一起评估——第二条语句的风险就此不被计数。命中项会把找到的字符
  列出来，报告里的语句条数也仍然是真实的条数。
  它抓不到全角**字母**（`Ａ`、`ｔ`）：`is_ident_start` 用的是 `is_alphabetic()`，全角字母满足
  它，于是变成一个和合法中文标识符一模一样的词。全角**数字**（`１`）反倒跑不掉——它不满足
  `is_alphabetic()`，只能按标点分词。
- 入库的 SQL 是脱敏的，所以真正决定影响范围的那个字符串字面量
  （`created_at < '2024-01-01'`）在旧记录里依然看不见。数字正是为此保留的；本次
  会话内刚提交的记录还能对着原文审——见
  [审计库里存的是什么](review-model.zh-CN.md#审计库里存的是什么)。
